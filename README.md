# Universal Portable Package Builder — r1 test candidate

A standalone public GitHub Action repository for compiling **independent, headless NSIS-built PortableApps-style `.paf.exe`** packages from a **previously validated, assembled Windows PortableApps folder**. It also contains an **experimental** engine invoking an unchanged, checksum-verified official PortableApps.com Installer, and a reusable workflow for packaging an existing GitHub Release ZIP.

**Neither engine builds the underlying application or its launcher.** The caller supplies a real `AppNamePortable.exe`, metadata, app binaries, icons and any application-specific portable storage/recovery code. This project does not change Brave, OBS, Thunderbird, Komorebi or any other application builder.

**Important:** The independent NSIS installer is **not** generated by the official PortableApps.com Installer. The `.paf.exe` extension alone does not constitute official certification, full Format compliance or a license to redistribute the underlying application. The *official* engine will only claim official-tool provenance when a genuine unmodified tool downloaded from an authenticated HTTPS URL passes an explicitly supplied vendor checksum and generates the output. Official-tool headless behavior is not confirmed for large browsers.

## Files

- `action.yml`: composite action usable in an existing Windows build job, no second runner.
- `nsis/community-installer.nsi`: reusable NSIS installer with same-volume staging, App/Other/launcher backup, rollback and cleanup of obsolete binaries; no Data payload or Data deletions.
- `scripts/build.ps1`: metadata, Windows PE, input and output verification, bounded compilation, checksum output.
- `scripts/build-official.ps1`: separately identified official-tool attempt with checksum and headless timeout.
- `scripts/download-release.ps1`: explicitly named GitHub Release ZIP download, SHA256SUMS check and safe extraction.
- `.github/workflows/portable-paf-from-release.yml`: callable workflow for another repo to produce and publish an installer from an existing release.
- `.github/workflows/self-test.yml` + `tests/`: fast Windows synthetic install/upgrade/rollback tests. Manual trigger only.
- `examples/`: ready-to-copy caller snippets.
- `docs/`: safety notes, integration and setup guide.

## 1. Publish the universal repository using GitHub Desktop

1. Download and extract the ZIP. The contents include hidden `.github` and `action.yml`.
2. Open GitHub Desktop → **File → New repository** → enter `portable-package-builder`.
3. Choose a local repository folder. Use **Repository → Show in Explorer** and copy the extracted contents into that folder.
4. Back in GitHub Desktop, commit `Initial universal package builder r1` and click **Publish repository**. **Public** is recommended so both public and private application repositories may reuse this action. Creating it public does not make other repositories public.
5. In GitHub → **Actions → Universal Packager Self-Test → Run workflow**, run the fixture tests. They compile a tiny sample installer and check fresh install, upgrade, old version cleanup, Data protection, rollback, unrelated destination rejection and locked-file protection.
6. Only **after the test passes**, open the universal repo's **Releases → Draft a new release → Choose a tag → Create new tag `v1.0.0` on main**; publish the release. Do not claim it is production-verified until a real application installer has passed.
7. Keep the universal repo separate from the existing `vhick/portable-release-publisher` repo. Pin `@v1.0.0` (prefer the verified immutable full commit SHA in production) in application workflows.

If the test fails, do **not** publish `v1.0.0`; fix and rerun. Do not assume the files here have been live-tested in the current session.

## 2. Use as a packaging step in an existing builder

Once tag `v1.0.0` exists, insert the following after **your application's own build, native launcher tests, AppInfo validation and PortableApps staging** in a Windows job:

```yaml
- name: Build community PortableApps-style installer
  id: upb
  uses: vhick/portable-package-builder@v1.0.0
  with:
    source-dir: work/BravePortable
    output-dir: dist
    engine: custom-nsis
    running-exe: 'App\Brave\brave.exe'
    package-revision: r1
```

Outputs: `steps.upb.outputs.installer-file`, `installer-sha256`, `app-id`, `app-version`.

Continue with **your current** release publisher:

```yaml
- uses: vhick/portable-release-publisher@v1.1.1
  with:
    files: 'dist/*.zip;dist/*.paf.exe'
    tag: portable-v1.98.63-brave-universal-nsis-r1
    keep-releases: '3'
    prune: 'false'
    dry-run: 'true'
- uses: vhick/portable-release-publisher@v1.1.1
  with:
    files: 'dist/*.zip;dist/*.paf.exe'
    tag: portable-v1.98.63-brave-universal-nsis-r1
    keep-releases: '3'
    prune: 'false'
    dry-run: 'false'
```

The example tag is for Brave v1.98.63 only; other builders must generate tags based on their own actual version and packaging revision. Existing release tags must not be overwritten.

## 3. Repackage an existing released ZIP, without rebuilding the application

Copy `examples/caller-workflow.yml` into the **application builder's** `.github/workflows/build-paf-from-release.yml`. After publishing the shared action's `v1.0.0` tag, run that workflow in the application repo with:

- `source_tag`: existing validated ZIP release (e.g. `portable-v1.98.63-brave-r7`).
- `source_asset`: exact ZIP name (e.g. `BravePortable_1.98.63_brave-r7_Win64.zip`).
- `output_tag`: a **new** `portable-...` release tag, not the old ZIP tag.
- `publish`: set `true` only when you're ready to publish. `false` runs checks but does not retain a downloadable artifact, to avoid GitHub Actions artifact storage.

The reusable workflow runs in the **calling builder's** repository context. It uses `GITHUB_TOKEN` to read that repository's release, verifies SHA256SUMS.txt, extracts the ZIP, invokes the shared action on a Windows runner, runs the existing publisher in dry-run mode, then (when opted in) publishes to the **calling repository**. No personal access token, fork or duplicate Brave compilation is required.

**Important:** `v1.0.0` is a proposed future tag. It does not exist until you publish the shared repository and create it. Do not paste the example before that step.

## 4. Official installer engine — experimental

Set `engine: official` and supply **both** `official-tool-url` (genuine HTTPS distribution) and `official-tool-sha256` (the vendor-published 64-character SHA-256). The builder then downloads, verifies, extracts and executes the **unmodified** PortableApps.com Installer with a bounded timeout. It fails if there is no uniquely identified official output. This path is experimental: the existing Brave r7 attempt timed out. Changing to a shared repo does **not** solve that problem automatically. Do not guess a checksum, silently bypass verification or relabel an independent NSIS installer as official output.

## 5. Installer upgrade behavior

- **Replaces** managed `App`, `Other`, and the root launcher from the new package; old version-numbered binary directories no longer accumulate after successful upgrades.
- **Preserves** the complete `Data` folder (files, profile, caches, TraceGuard and completely empty directory trees).
- Rejects an existing installation whose `AppID` differs, a nonempty unknown destination, or a locked root launcher/optional `running-exe`.
- Before changing an existing install, extracts new files to `.__UPB_Stage`, then renames old managed files into `.__UPB_Backup`. On an ordinary failed install, it attempts to restore the original managed files; on success, it removes the old managed backup.
- If Windows crashes or a filesystem error interrupts the upgrade, the reserved backup remains and future installs **stop instead of deleting it**. Inspect and manually recover the backup. No software can guarantee atomic durability across abrupt power loss or disk failure.
- App and Other are **managed application directories**. User-added plugins/settings must be in Data or handled by an application-specific migration; otherwise they may be replaced along with obsolete binaries. The installer cannot generically determine which arbitrary files outside Data belong to a user.
- Never run upgrade while the app or child processes are active. Exclusive-use checks on named binaries are safeguards, not a complete process-tracking solution. Backup your Data before real upgrades.

## 6. Scope and limitations

- Host Windows is required for compiled NSIS and real installation tests. Tested locally in this environment: static verification, not a Windows run. See `docs/VALIDATION.md`.
- No bundled app binaries, copyrighted app logos, installer EXEs or external fonts. Synthetic tests use the built-in Windows `where.exe` copied to the fixture, and a tiny original test icon.
- Installer is self-contained, requires no admin rights, does not write system registry, does not disable antivirus or obfuscate scripts.
- Standard PortableApps Menu recognition depends on correct supplied appinfo.ini and compiled launcher, not merely the installer filename.
- Avoid public distribution unless the original application licenses and branding permissions allow it; see PortableApps Format permissions.
- No scheduled checks; shared action uses a GitHub-hosted Windows runner in the calling job. Build outputs are published only through the separately maintained release publisher.
